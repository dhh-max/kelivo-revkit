# APK 分析防崩溃与性能优化方案

> 本文档描述 Kelivo RevKit 在 APK 解包与深度分析场景下的防崩溃策略、性能优化机制及配置参考。
> 目标：彻底解决大体积 APK / 多 DEX APK 分析时模型 OOM 崩溃、超时无响应等问题。

## 1. 问题背景

移动端 AI 助手在分析大型 APK 时，常见以下崩溃场景：

| 症状 | 根因 | 触发条件 |
| --- | --- | --- |
| 模型 OOM 崩溃 | 反编译全量 DEX/SO 代码一次性注入上下文，超出模型 token 上限 | APK > 50MB 或含 3+ DEX 文件 |
| 分析超时无响应 | 全量字符串/方法扫描耗时过长，阻塞前台交互 | SO 文件 > 20MB 或字符串池 > 10万条 |
| 进程被系统杀死 | 内存峰值过高，触发 Android Low Memory Killer | 解包+分析同时进行，内存占用 > 512MB |
| 中断后无法恢复 | 无断点续传机制，中断后需从头开始 | 设备重启/进程被杀/手动退出 |

## 2. 核心策略

### 2.1 分片增量分析

将大型 APK 的分析任务拆分为多个独立分片，逐片分析、逐片返回结果。

```
APK → 分片策略决策 → 分片1分析 → 返回结果 → 分片2分析 → 返回结果 → ... → 汇总报告
```

**分片维度：**

| 分片类型 | 切分依据 | 适用场景 |
| --- | --- | --- |
| DEX 分片 | 按 `classes*.dex` 文件自然分片 | 多 DEX APK |
| 类分片 | 按 `class_defs` 数量均分（默认每片 500 类） | 单 DEX 类数量过大 |
| 字符串分片 | 按字符串池索引范围分片（默认每片 1万条） | 字符串搜索/扫描 |
| SO 分片 | 按 `.so` 文件逐个分析 | 多 native 库 APK |

**内存控制：**

- 每个分片分析完成后立即释放该分片的内存占用
- 设置内存阈值监控：当可用内存低于 100MB 时暂停分析，等待 GC 回收后继续
- 分片间设置 200ms 间隔，给系统留出 GC 窗口

### 2.2 分析超时降级机制

```yaml
# 默认配置
analysis_timeout: 120s        # 单次分析超时阈值
degrade_strategy: lightweight  # 超时后降级策略
```

**降级路径：**

```
深度分析模式（全量反编译 + 语义分析）
  ↓ 超时触发
标准分析模式（基础反编译 + 关键字匹配）
  ↓ 再次超时
轻量分析模式（仅元信息 + 权限 + 组件 + SDK 列表）
```

| 模式 | 耗时 | 内容范围 | 适用场景 |
| --- | --- | --- | --- |
| 深度分析 | 30s~5min | 全量反编译代码 + 语义分析 + 恶意代码检测 + 混淆标记 | 需要完整逆向分析 |
| 标准分析 | 10~30s | 基础反编译 + 关键字匹配 + 权限/组件审计 | 日常安全排查 |
| 轻量分析 | <10s | 仅元信息/权限/组件/SDK 列表，无反编译 | 快速预筛 |

### 2.3 离线后台分析

大型 APK 分析自动转入后台任务队列，不阻塞前台对话。

**任务生命周期：**

```
用户发起分析 → 判断 APK 大小 → 大于阈值(50MB)则转入后台队列
  → 后台 Worker 执行分析 → 实时更新进度
  → 分析完成 → 推送通知 → 用户可查看完整报告
```

**后台任务能力：**

- 进度查询：当前步骤 / 总步骤 / 预估剩余时间
- 暂停 / 继续：用户可主动暂停后台分析
- 超时自动取消：后台任务最长运行 30 分钟，超时自动取消并通知用户
- 结果持久化：分析结果写入本地文件，即使 App 被杀也可恢复

### 2.4 断点续传

**断点记录点：**

| 阶段 | 记录内容 | 恢复动作 |
| --- | --- | --- |
| 解包阶段 | 已解包文件列表 + 当前处理文件 | 跳过已解包文件，从断点继续 |
| DEX 分析 | 已分析 DEX 文件 + 已分析类索引 | 跳过已分析部分，从断点继续 |
| SO 分析 | 已分析 SO 文件列表 | 跳过已分析 SO，从断点继续 |
| 字符串扫描 | 已扫描字符串索引范围 | 跳过已扫描范围，从断点继续 |
| 报告生成 | 各阶段分析结果是否已完成 | 补齐未完成阶段后生成报告 |

**断点存储：**

- 断点文件存储在 `<app_private_dir>/analysis/<apk_hash>/checkpoint.json`
- 每完成一个分片立即写入断点（原子写入：先写临时文件再 rename）
- App 启动时扫描未完成的断点，提示用户是否恢复

### 2.5 混淆代码智能标记

自动识别 ProGuard/R8 混淆特征，标记混淆类/方法：

**识别规则：**

| 特征 | 判定条件 |
| --- | --- |
| 类名混淆 | 类名为单字母（a~z）或 `a/b/c` 格式 |
| 方法名混淆 | 方法名为单字母或 `a` 格式 |
| 字段名混淆 | 字段名为单字母 |
| 包名混淆 | 包名为单字母 |
| 资源混淆 | 资源文件名极短（1~2字符）且无语义 |

**恢复能力：**

- 支持加载 `mapping.txt`（ProGuard 输出）自动恢复原始符号
- 支持加载 crash mapping 文件恢复混淆堆栈
- 标记结果导出为 JSON，可导入 JADX 等工具

### 2.6 恶意代码预检测

内置恶意特征库，在分析阶段自动标记风险代码段：

| 检测类别 | 特征模式 | 风险等级 |
| --- | --- | --- |
| 加密货币挖矿 | `Mining`/`Pool`/`stratum`/`xmrig`/`coinhive` + 网络连接 | 高危 |
| 恶意扣费 | `sendTextMessage` + premium shortcode + 静默发送 | 高危 |
| 隐私窃取 | 通讯录/SMS/位置 上传 + 混淆URL + 后台运行 | 高危 |
| 广告弹窗 | `loadAd`/`InterstitialAd` + 锁屏显示 + 不可关闭 | 中危 |
| Root 利用 | `su`/`Superuser`/`magisk` + `Runtime.exec` | 中危 |
| 动态加载 | `DexClassLoader`/`PathClassLoader` + 远程下载 | 中危 |

## 4. 性能基准

| APK 规格 | 传统模式 | 优化后（轻量） | 优化后（标准） | 优化后（深度） |
| --- | --- | --- | --- | --- |
| < 10MB / 1 DEX | 5~15s | <3s | 5~8s | 10~20s |
| 10~50MB / 1~2 DEX | 30~120s | <5s | 15~30s | 60~120s |
| 50~100MB / 3~5 DEX | 崩溃/超时 | <10s | 30~60s | 120~300s |
| > 100MB / 5+ DEX | 崩溃 | <15s | 60~120s | 300~600s |

## 5. 监控与告警

- 内存使用量实时监控：超过阈值时在 UI 显示内存警告
- 分析进度可视化：进度条 + 当前步骤描述 + 预估剩余时间
- 崩溃日志自动收集：分析过程中发生的异常自动记录到 `<app_private_dir>/analysis/crash_log.txt`
- 降级事件通知：当分析从深度模式降级为轻量模式时，明确告知用户降级原因
